Dated topic list: data systems

October 14 / 16 · Storage and reliable versions

Parquet groups data by columns, so a query needing only a few columns can avoid reading others. A data lake stores flexible raw data; a warehouse organizes prepared reporting data; a lakehouse adds reliable table management to lake storage. In a star, facts record events and measures; dimensions supply context.

A coordinated table version identifies the files belonging together. Finish and validate replacement files before atomically committing the new version: a reader sees a consistent old or new snapshot, rather than a mixture.

October 19 · Pipelines and changing sources

ETL prepares data before loading the destination; ELT loads first and transforms there. Bronze retains received records; silver holds accepted, standardized records; gold serves reports. State what one row means at each layer. A retry should be idempotent: replaying the same input does not double the result.

A renamed field changes the schema; dollars changing to cents can preserve names and numeric types while changing meaning. An adapter maps a declared source version into the names and units downstream users expect.

October 21 / 23 · Checks, corrections, and history

Executable checks can test required columns/types, unique keys, allowed values/units, and expected history. A passing job or schema check alone does not prove the report is correct. Checks establish only the conditions they actually test.

For a lakehouse correction, the table's recorded snapshot determines which files count; a stray file is not automatically part of the table. Time travel reads an older version. It does not itself undo a correction or make that version current.

October 26 · Performance and cost

Partition pruning skips irrelevant groups of files; column selection and statistics can skip more data. A plan describes intended work; a profile shows what actually ran. Moving data and uneven work (skew) can dominate runtime. Include preparation cost when comparing approaches; a cached result can be fast but stale.

Dated topic list · continued

From location data to model evaluation

October 28 / 30 · Geospatial walkthrough

GeoPandas works with geometry such as points and area boundaries. A key-based merge attaches a population table to the corresponding area boundaries. Check both the row count and unmatched keys. The coordinate reference system (CRS) tells you what coordinates and their units mean; area from coordinates in feet is in square feet, not square miles. A map of total population answers a different question from a map of population per unit area.

November 2 · Charts, storytelling, and data cards

Choose a chart for the question: bars compare categories; a line shows change over time. State a claim the displayed data actually supports. A data card records context, source, coverage, and limitations; documentation makes limitations visible but does not repair missing or biased evidence.

November 4 / 6 · Streaming clocks and late data

Bounded input has an end; an unbounded stream keeps arriving. Batch/stream choices concern how work is processed; frequent batches do not make event time and arrival time identical. Event time is when something happened; processing time is when the system handles it. A window groups observations over time.

A watermark estimates progress in event time; it is not proof that every event has arrived. Waiting longer can include more late data but costs latency and retained state. Finalizing sooner needs a policy for later arrivals and a clear explanation of possible incomplete results.

November 13 · First KNN model and safeguards

Features are inputs; the target is the answer being predicted. Split into training and held-out test data. Fit scaling on training data only, then apply that same transformation to test data. Fitting a missing-value fill or other learned preparation also belongs inside the training boundary.

Leakage means information unavailable at prediction time sneaks into training or evaluation. Remove features that reveal the outcome or come from the future. Compare with a simple baseline, such as always predicting the most common class.

Precision: of the cases we flag, how many really need action? Recall: of all cases needing action, how many did we find? Accuracy alone can hide missed rare cases. If staff can contact only a few people, evaluate the ranked action list and its tradeoff between useful contacts and missed needs.

November 16 / 18 · Model families and choosing a first fit

Review the ML reference next: task type, preparation, over/underfitting, model strengths and limits. Then use the additional-family overview. Name a defensible first choice and a limitation; test it on held-out data rather than declaring a universal winner.

1 / 7

Too simple, too memorized, just right

Every model sits somewhere on one spectrum. Learn to spot where - from the training score and the test score - and
you can answer most overfitting questions without any math.

Underfitting - too simple

The model misses the real pattern. It does poorly on
training data 

and

 poorly on test data.

Example:

 fitting a straight line to a pattern that

clearly curves.

Fix direction:

 a more flexible model, or better

features.

Overfitting - memorized, not learned

The model fits the training data almost perfectly -
including its noise and quirks - then falls apart on
new data.

Tell-tale sign:

 

great training score, much worse

test score.

Fix direction:

 a simpler model, more training data, or

regular checks on held-out data.

Just right = generalizes.

 Training and test scores are reasonably close, and both are decent. The model

captured the pattern, not the noise. Perfect training accuracy is a warning sign, not a trophy.

Bias and variance - the same story, in quiz language

High bias

 goes with underfitting: the model is too rigid and keeps making the same kind of mistake.

High variance

 goes with overfitting: the model is too sensitive, and small changes in the training data swing its

answers a lot.

There is a 

trade-off

: making a model more flexible usually lowers bias but raises variance. The goal is the

balance in the middle, not either extreme.

Why we split the data

If you judge a model only on the data it trained on, an overfit model looks like the best model. Splitting data into a

training set

 and a separate 

test set

 is what exposes that. A validation set, when used, sits in between: you tune

choices on it, and keep the test set untouched for the final honest check.

Categorical data: labels are not numbers

A

Why you cannot just number them 1, 2, 3:

 If Downtown = 1, Suburb = 2, and Rural = 3, the model reads that

November 16 / 18 · Additional ML overview

More families, same choice

Keep the same task → data → strength → limitation reasoning. Recognize these families at overview level; you do not need their formulas.

FamilyCore idea and useful fitLimit to remember
LDA / QDAGenerative classifiers describe the feature patterns within each class. LDA shares a spread assumption; QDA allows separate spreads.QDA is more flexible and needs more examples; the assumed class shapes may fit poorly.
Naive BayesA simple generative classifier that treats inputs as independent within each class.Strongly related inputs can count much the same evidence twice.
Ridge / lassoShrink feature effects to limit overfitting. Lasso can set some effects to zero.Important effects can be shrunk too far; simpler does not automatically mean better.
Splines / GAMsUse smooth curves; a GAM adds separate feature effects. Useful for readable, curved relationships.Separate additive curves can miss effects that depend on other features.
Neural networks / CNNsLearn flexible patterns. A CNN is designed for spatial patterns such as image regions.Needs enough suitable data and is harder to explain. A CNN is not automatically best for a table.
Bagging / random forestBagging combines trees fitted to resampled data. A forest also varies candidate features at each split, making trees less alike.Shared errors survive averaging; adding similar trees cannot fix every problem.
XGBoost / LightGBM / CatBoostBoosting implementations with different practical designs: XGBoost supports sparse/missing inputs; LightGBM emphasizes efficient training; CatBoost handles categories with safeguards against outcome leakage.All still need tuning and held-out checks; no name guarantees the best model for your data.
StackingA second model learns to combine other models' predictions.Train it using predictions for cases excluded from the corresponding first-level fit, so training-fit answers do not leak in.

One last check

A family is a starting bet about the data. A medium-sized table does not become an image problem because a neural network is fashionable. Choose a simple baseline, test credible alternatives, and state the cost or limitation you accept.

Short-answer practice · 1–5

Reason in a sentence or two

Use the guide. Each question has at most two brief asks. Three ruled lines are provided.

1. Storage and reliable versions · Oct 14 / 16

A report needs only two columns from a wide sales table. Why might Parquet help? During a correction, why should readers use one committed file version rather than every file in the folder?

2. Pipelines and retries · Oct 19

A team loads raw purchases before cleaning them. Is this ETL or ELT? What should happen to the sales total when the exact same batch is retried?

3. Changing sources and checks · Oct 19 / 21

A vendor changes amounts from dollars to cents without changing the column name or numeric type. Why can the schema check pass while the report is wrong? Describe one check that would catch this unit error.

4. Corrections and history · Oct 23

A corrected file sits beside the original but is not in the table’s recorded snapshot. Should a table query count it automatically? Does reading yesterday’s version undo today’s correction?

5. Performance and cost · Oct 26

A query asks for one month but scans every month. Name one way to skip unnecessary work. Give one reason a cached result could be fast but unsuitable.
